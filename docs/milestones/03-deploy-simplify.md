# Веха 3. Упрощение выкладки

Документ задачи: заменить TypeScript-команду выкладки Watchlist v2 на `cora` коротким bash-скриптом на той же раскладке сервера. Исследование и выбор автора – 2026-10-03, ревизия `4c9e05b`. Исходное решение вехи 3 и его основания – в [документе вехи 3](03-deploy-v2.md), общие решения – в [плане](../plan.md).

## Задача и контекст

Веха 3 сделала выкладку и откат одной командой с ноутбука: `pnpm deploy:v2 [коммит]` и `pnpm rollback:v2`. Код – `deploy/command` на TypeScript (1807 строк кода и 2710 строк тестов), рядом `deploy/setup-server.sh` (первичная настройка сервера, 337 строк), `deploy/Caddyfile`, `deploy/compose.yaml` и `deploy/README.md`. На `cora` всё работает: `current` – `a12503d`, `previous` – `fb4f020`, 5 каталогов релизов. Чек-лист iPhone не пройден. Полировка по итоговому ревью лежит в ветке `deploy-polish` (`fc1d39b`), не просмотрена и не слита.

Автор считает выкладку переусложнённой: нужен минимальный набор для выкладки приложения на сервер. Удалённого репозитория и CI нет.

Задача – заменить `deploy/command` bash-скриптом около 150 строк, сохранив команды `pnpm deploy:v2` и `pnpm rollback:v2`, раскладку и состояние `cora`, `Caddyfile` и `compose.yaml`. Упрощаем под v2 без пользователей; к CI, образам и очистке возвращаемся в вехе 6.

Не входит: CI и удалённый репозиторий; выкладка образами; очистка старых релизов; изменения `setup-server.sh`, кроме установки `curl`, если его нет на `cora`, и пометки для `shellcheck`; ветка `deploy-polish` – выбрасывается.

Ограничения: на `cora` – только по разрешениям автора в `.claude/settings.local.json` (`pnpm deploy:v2`, `pnpm rollback:v2`, `bash deploy/setup-server.sh`) или по его поручению; `viola-selectel` и `hope-vdsina` не трогать; том `caddy_data` не удалять.

### Что автор назвал обязательным

- Заголовки Caddy против ложного `304` для `sw.js` (документ вехи 3, раздел «Исследование»).
- Сборка ровно выкладываемого коммита.
- Откат одной командой.
- Отказ второй выкладке, пока идёт первая: агенты работают в разных worktree.

## Поведение

Сейчас `pnpm deploy:v2 [коммит]` собирает коммит во временном worktree, держит блокировку отдельным соединением `ssh`, доставляет релиз, переключает указатели, проверяет с ноутбука по HTTPS каждый файл и заголовки, при неудаче возвращает прежний релиз и чистит старые релизы; Ctrl+C действует в три ступени. `pnpm rollback:v2` меняет `current` и `previous` местами с той же проверкой.

После изменения – для автора и агента:

- `pnpm deploy:v2 [коммит]` (по умолчанию `HEAD`):
  - если в рабочем дереве есть незакоммиченное или неотслеживаемое – предупреждение, что в релиз оно не попадёт; если в коммите нет `deploy/Caddyfile` или `deploy/compose.yaml` – отказ до сборки;
  - если блокировка на сервере занята – сразу отказ «Другая выкладка или откат уже идут» (код 75), без сборки; та же проверка повторяется под самой блокировкой;
  - если релиз коммита уже на сервере – без сборки; иначе сборка во временном worktree и доставка одним сеансом `ssh`;
  - на сервере: сверка сумм, `caddy validate`, строка журнала, переключение `previous` и `current`, `compose up`, `reload`, проверка сайта с самого сервера в пределах 60 с (300 с, если `current` ещё не было – выпуск сертификата);
  - успех – «готово: releases/<хеш>»;
  - неудача до переключения (суммы, `validate`) – отказ, на сервере ничего не меняется;
  - неудача после переключения – указатели возвращаются как были, прежний релиз поднимается (`compose up`, `reload`), в журнал пишется его строка, сообщение называет причину; если не удался и сам возврат – сообщение, что указатели возвращены, а сервисы нет, и команды осмотра;
  - выкладка коммита, который уже `current`, – только проверка, без возврата.
- `pnpm rollback:v2` – обмен `current` и `previous` под той же блокировкой, `compose up`, `reload`, та же проверка и тот же возврат; отказ, если `previous` нет, совпадает с `current` или его каталога нет, с последней строкой журнала.
- Ctrl+C или обрыв `ssh`: скрипт на сервере доводит начатое до конца сам, весь его вывод пишется в `/opt/lists/deploy.log`. Команда на ноутбуке говорит смотреть исход там – обязательно перед повторным `rollback`: откат меняет указатели местами, и повтор вернул бы плохой релиз. Если сервер остался между шагами, повтор той же команды доводит дело.
- Старые релизы не удаляются; в README – команда, которая удаляет всё, кроме `current` и `previous`.

Что пропадает по сравнению с сейчас: многоступенчатый Ctrl+C и отслеживание потери блокировки, запись о владельце блокировки (`deploy.lock.owner`), различение «нет ответа» и «неверный ответ» с повторами, проверка с ноутбука каждого файла по суммам, автоматическая очистка, unit-тесты команды.

## Решение

Решения автора (2026-10-03, опросник исследования): выкладка с ноутбука, к CI вернуться позже; упрощаем под v2; простой автоматический возврат; выборочная проверка; Ctrl+C и обрыв без особой обработки; код выкладки проверяется прогоном на `cora` и `shellcheck`, без набора на контейнере; `setup-server.sh` остаётся; без очистки; `shellcheck` – из `brew` в `pnpm check`; вариант – bash на текущей раскладке.

Части:

- `deploy/deploy.sh` – локальная часть для macOS `/bin/bash` 3.2: разбор команды, поиск коммита (`git rev-parse --verify --end-of-options <коммит>^{commit}`), предупреждение о рабочем дереве, проверка файлов в коммите, быстрый отказ при занятой блокировке, проверка `test -d releases/<хеш>` на сервере, сборка, запуск серверной части. Хост (`lists`), корень (`/opt/lists`) и сайт (`v2.watchlist.acherenkov.com`) – константы, без переменных `LISTS_*` прототипа: забытый экспорт не должен перенаправить выкладку.
- `deploy/remote.sh` – серверная часть для bash 5.2. Локальная часть читает её из файла (`$(<…)`) и передаёт в `ssh lists "bash -c '…' _ <аргументы>"` с экранированием апострофов, архив релиза – в stdin того же сеанса. Отдельный файл – чтобы `shellcheck` проверял серверную часть как обычный скрипт.
- Сборка: `git worktree add --detach` во временный каталог, `APP_VERSION` снимается, `pnpm install --frozen-lockfile --prefer-offline`, `pnpm --filter watchlist build`; релиз – `site/` из `apps/watchlist/dist`, `Caddyfile`, `compose.yaml` и `SHA256SUMS` (`shasum -a 256` по файлам `site/` в порядке `LC_ALL=C sort`); архив – `COPYFILE_DISABLE=1 tar --no-xattrs -czf`. Временный worktree и каталог убираются при выходе.
- Серверная часть по порядку:
  1. `cd /opt/lists`, `exec 9>>deploy.lock`, `flock -n 9` или отказ с кодом 75; `trap '' HUP`; вывод – `exec > >(trap '' PIPE; exec tee -ap deploy.log) 2>&1`: без этой строки `docker` и `caddy` на закрытом после обрыва выводе получают SIGPIPE и запускают ложный возврат;
  2. приём релиза в чистый `tmp/`: `timeout 300 tar -xzf - --no-same-owner`, сразу после – `exec </dev/null`, `chmod -R u=rwX,go=rX`, `sha256sum -c --quiet --strict`, `mv` в `releases/<хеш>`; лежащий релиз не принимается заново;
  3. `caddy validate` релиза до переключения – образом из `compose.yaml` релиза, без разбора вывода `config --images`; кандидат – `docker compose -f releases/<хеш>/compose.yaml run --rm --no-deps -T -v <каталог релиза>:/release:ro caddy caddy validate --config /release/Caddyfile --adapter caddyfile` (проверить на `cora`, при неудаче выбрать другой способ без разбора вывода);
  4. переключение – как сейчас: строка `<UTC-время> <хеш>` в `releases.log`, затем `previous`, затем `current`; ссылка относительная (`releases/<хеш>`), каждая – `ln -sfn` во временное имя и `mv -T`;
  5. `docker compose -f current/compose.yaml up -d --wait --wait-timeout 120`, затем `docker compose -f current/compose.yaml exec -T caddy caddy reload --config /srv/current/Caddyfile --adapter caddyfile`;
  6. проверка сайта с сервера: `curl --resolve v2.watchlist.acherenkov.com:443:127.0.0.1`; срок – по времени (`SECONDS`), не числом проходов: при зависшем Caddy 30 проходов по 15 с на запрос длились бы около часа;
  7. каждый шаг после переключения проверяется явно (`|| …`), без ловушки `ERR`: при `set -E` она наследуется подстановками команд, и в bash 3.2 сбой `curl` внутри `$(…)` запускал возврат из подоболочки;
  8. возврат – указатели ровно как были до выкладки (`previous` удаляется, если его не было), строка прежнего релиза в `releases.log` (README держит инвариант «последняя строка журнала – `current`»), `compose up` и `reload`; на первой выкладке возвращаться некуда – сообщение и состояние указателей.
- Выборочная проверка: `/`, `/index.html` и `/sw.js` отвечают `200` и совпадают с файлами релиза (`cmp`); у `index.html` и `sw.js` – `Cache-Control: no-cache`, нет `ETag` и `Last-Modified`; `X-Robots-Tag: noindex`; `sw.js` с `If-None-Match: *` и с `If-Modified-Since` в будущем – `200`; один файл из `assets/` – `immutable`; `/api/x` – `404`. Сообщение называет первую нарушенную защиту.
- Откат – обмен указателей под той же блокировкой с теми же `up`, `reload`, проверкой и возвратом.
- Код возврата 255 у `ssh` и прерывание на ноутбуке (`INT`, `TERM`) – подсказка `ssh lists tail /opt/lists/deploy.log` и предупреждение про повторный `rollback`.
- `package.json`: `deploy:v2` – `/bin/bash deploy/deploy.sh deploy`, `rollback:v2` – `/bin/bash deploy/deploy.sh rollback` (явный `/bin/bash`: проверено на 3.2, а `bash` из `PATH` может оказаться из brew); `check-types` – без `deploy/tsconfig.json`; `shellcheck deploy/*.sh` – в `lint` или отдельным скриптом, который входит в `pnpm check` и хук `.husky/pre-push`; без установленного `shellcheck` проверка падает с подсказкой `brew install shellcheck`. В `deploy/setup-server.sh` `shellcheck` находит одно замечание SC2086 (info) – намеренное разбиение `$PACKAGES` в вызове `remote_script`; `shellcheck` завершается с ошибкой и на info, поэтому нужна пометка `# shellcheck disable=SC2086` с причиной. Имена команд и разрешения в `.claude/settings.local.json` не меняются.
- Удаляются `deploy/command`, `deploy/tsconfig.json` и `deploy/command/**/__tests__/**` из `include` в `vitest.config.ts`.
- `CODESTYLE.md`: убрать правила о `deploy/command` и проводке; записать, что скрипт выкладки – исключение из правила мутаций и проверяется прогоном на `cora` и `shellcheck`; добавить правила: bash-скрипты проверяются `shellcheck` в `pnpm check`; локальная часть выкладки – для `/bin/bash` 3.2, серверная – для bash 5.2: без ассоциативных массивов, `mapfile` и `${x,,}`, heredoc с апострофом внутри `$(…)` на 3.2 не разбирается; возврат после неудачи не делать ловушкой `ERR` при `set -E`.
- `docs/testing.md`: убрать строку о `deploy/command` и таблицу сценариев выкладки, сослаться на раздел «Проверка» README или этого документа.
- `deploy/README.md`: оставить устройство сервера, раскладку и её причины, сломанный `sw.js`, обновление Caddy и `docker-compose-v2`, ручные действия; переписать или убрать «Блокировку», «Прерывание и потерю блокировки», «Очистку старых релизов», «Проверку по HTTPS» и `deploy.lock.owner`; добавить `deploy.log` (растёт без ограничения) и команду удаления старых релизов.
- `AGENTS.md`: строка о README («блокировка, прерывание, очистка»); в «Окружение» – `shellcheck` из brew.
- `setup-server.sh`: `curl` в список пакетов, если на `cora` его нет.

Порядок работы:

1. Написать `deploy.sh` и `remote.sh` и пройти проверку на `cora` (раздел «Проверка»), пока TypeScript-команда жива: обе открывают `/opt/lists/deploy.lock` одинаково (`9>>`, `flock -n`) и исключают друг друга (сверено по коду).
2. Отдельным коммитом – переключить `package.json` и удалить `deploy/command`, чтобы откат перехода был `git revert`.
3. Документы: README, `CODESTYLE.md`, `docs/testing.md`, `AGENTS.md`; удалить ветку `deploy-polish` и её worktree.
4. Чек-лист iPhone вехи 3; затем закрыть веху 3 – документ вехи 3, план.

Текст прототипа – в приложении; отличия итогового скрипта от прототипа перечислены выше.

## Основания

Выбран вариант 1 из таблицы ниже.

- Проверен лучше остальных: прототип прогнан на настоящих `sshd` и Caddy, со сломанными `Caddyfile`, сбоями `compose up` и `reload`, промежуточными состояниями и обрывом `ssh`. Итоговый скрипт переписывает возврат, поэтому эти проверки повторяются на `cora` (раздел «Проверка»).
- Не требует менять `cora`: каталог релиза, `SHA256SUMS`, строки `releases.log`, относительные ссылки `current` и `previous` и способ открытия `deploy.lock` совпадают с тем, что оставила TypeScript-команда (ревью сверило по коду), поэтому первая выкладка новым скриптом ляжет поверх `a12503d`.
- Caddy не пересоздаётся: выкладка и откат – `reload` без отказов.
- Сохраняет всё обязательное: тот же `Caddyfile` и проверка ложного `304`, сборка ровно коммита во временном worktree, откат одной командой за доли секунды, отказ второй выкладке под `flock -n`.
- Ошибка выбора между 1 и 2 стоит около 150 строк. Главный плюс варианта 2 – один механизм для статики и образа сервера – нужен только с вехи 6; тогда и сравнить «образ сервера при каталогах релизов» со «всё образами».
- Варианты 3–7 не проще варианта 1 при тех же гарантиях (раздел «Исследование»).

Принятые потери: многоступенчатый Ctrl+C (сервер дорабатывает сам), различение сбоя сети и неверного ответа (проверка идёт с сервера, сети ноутбука в ней нет), проверка с ноутбука каждого файла по суммам (содержимое сверено `sha256sum -c` при доставке, заголовки зависят от пути, а не от файла), очистка (релиз около 1 МБ при 50 ГБ диска). Без набора сценариев на контейнере в итоговом коде остаются непроверенными первая выкладка на пустой сервер и обрыв между перестановками указателей, а правки скрипта в вехе 6 – без регрессионного набора: первая выкладка бывает только на новом сервере и видна сразу, обрыв между указателями исправляет повтор команды. Пересмотреть, если скрипт заметно вырастет или такие случаи начнут встречаться.

### CI и `git push` на сервер (`researcher`, первоисточники прочитаны 2026-10-03)

Вывод: ни один вариант не даёт выкладку веток из worktree агентов, откат и защиту от параллельной выкладки с меньшей настройкой, чем короткий скрипт с ноутбука; каждый требует то же плюс новую часть. CI полезен в вехе 6 – сборка образа сервера под amd64 и реестр, – для статики в 1 МБ почти ничего не даёт.

- Сборка на ноутбуке (Mac arm64, Node 24.16.0, pnpm 12.3.4): `pnpm install --frozen-lockfile` при прогретом хранилище – 1,3 с, сборка Watchlist – 1–4 с, пик памяти – 466 МБ; хранилище pnpm – 882 МБ, `dist` – 896 КБ, 12 файлов.
- **GitLab.com, общие раннеры + `ssh`**: 400 минут в месяц на namespace, квота `a.cherenkov` общая с `abc/cloud`, который уже упирается в лимит (`abc/cloud/docs/decisions.md`). Защищённые переменные видны только защищённым веткам: ключ от `cora` для веток агентов пришлось бы сделать незащищённым – его увидит любая ветка с изменённым `.gitlab-ci.yml`. Очередь – `resource_group` (`oldest_first`). Повтор старого job выкатывает старый коммит поверх нового – `abc/cloud` защищается от этого сверкой с головой `master`.
- **GitLab.com, раннер `shell` на `cora`**: минуты не тратятся, но код любой отправленной ветки исполняется на `cora` с правами группы `docker`, то есть root; рядом с будущим токеном бота и базой это прямой риск (так же оценено в `abc/cloud`). На сервере – Node, pnpm, хранилище и обновления раннера.
- **GitHub Actions**: 2000 минут на Free; Россия в политике торгового контроля не закрыта, но в 2022 году блокировались аккаунты российских разработчиков. `concurrency` по умолчанию заменяет ожидающий запуск третьим – выкладка агента молча отменяется, нужен `queue: max`.
- **Forgejo или Woodpecker на `cora`**: ещё одна публичная служба на сервере, который нужен базе и сервису синхронизации; для одного пользователя не оправдано.
- **Голый репозиторий на `cora` + `post-receive`** (прототип на ноутбуке, цикл 8 с): Node, pnpm и `pnpm install` с lifecycle-скриптами от root на сервере; доступ `cora` к `registry.npmjs.org` не проверен. Подводные камни прототипа: `prepare: husky` пишет `core.hooksPath` в конфиг голого репозитория, и хук перестаёт вызываться (лечится `HUSKY=0`); `GIT_DIR` утекает в окружение хука, и номер версии не определяется (`unset GIT_DIR`); повторный push того же коммита хук не вызывает – нужен уникальный ref; код возврата `git push` не отражает отказ хука – агент должен читать строки `remote:`; `.husky/pre-push` гоняет проверки на каждый push, в том числе на `cora`.
- Правило `AGENTS.md` «Push – только по поручению автора» не различает удалённые репозитории: при CI или push на `cora` агент без слова автора выкладывать не сможет, пока правило не уточнено.
- Побочно: `pnpm install` текущей команды во временном worktree тоже запускает `husky`, который пишет `core.hooksPath` в общий конфиг репозитория; значение там уже такое же, вреда нет.

### Прототип bash-скрипта на текущей раскладке (`researcher`, 2026-10-03)

Прототип – один файл `deploy/deploy.sh deploy [коммит] | rollback` в worktree `deploy-sketch`, не закоммичен. Его текст – в приложении в конце документа. Проверен без `cora`: сервер – контейнер Ubuntu 24.04 (GNU tar 1.35, util-linux 2.39.3, coreutils 9.4, OpenSSH 9.6p1, bash 5.2) с настоящим `sshd` и настоящим Caddy 2.11; `docker` – заглушка, которая запускает этот Caddy; ноутбук – macOS `/bin/bash` 3.2.57.

Устройство: сборка во временном worktree коммита на ноутбуке, `tar` в stdin одного сеанса `ssh … bash -c '<серверная часть>'`; на сервере под `flock -n` – приём архива, `sha256sum -c`, `mv` в `releases/<sha>`, `caddy validate` в контейнере образа из `compose.yaml` релиза, строка журнала, `previous` и `current` через `mv -T`, `compose up -d --wait`, `caddy reload`, проверка сайта с самого сервера (`curl --resolve <сайт>:443:127.0.0.1`), при неудаче – возврат указателей, `compose up` и `reload` прежнего релиза. Откат – обмен указателей под той же блокировкой с той же проверкой.

| Часть | Строк (из них код) |
| --- | --- |
| Ядро: сборка, доставка, суммы, `validate`, указатели, журнал, `compose up`, `reload`, откат, лежащий релиз без сборки | 113 (87) |
| Выборочная проверка сайта с сервера | 19 |
| Проверка всех файлов по `SHA256SUMS` | 4 |
| Автоматический возврат | 7 |
| Очистка до 5 релизов по журналу | 10 |
| Предупреждение о незакоммиченном | 1 |

Что проверено:

- Сборка и выкладка настоящих коммитов `c6b3815`, `8c478bb`, `4c9e05b`: 8–9 с с прогретым хранилищем pnpm, лежащий релиз – 0,4 с, откат – 0,3 с; повторный откат отменяет первый; временные каталоги и worktree не остаются.
- Шесть `Caddyfile`, в каждом убрана одна защита (`no-cache`, `-ETag`, срезка `If-None-Match`/`If-Modified-Since`, `immutable`, `/api/` → `404`, `noindex`): проверка называет причину, указатели возвращаются ровно как были. Без срезки валидаторов `sw.js` с `If-None-Match: *` получает не `200` – тот самый ложный `304`.
- Подменённый `sw.js` (`sha256sum -c`) и неверный `Caddyfile` (`validate`) ничего не меняют на сервере; на первой выкладке возвращаться некуда, скрипт так и пишет.
- Вторая команда при занятой блокировке получает «Другая выкладка или откат уже идут» и код 75.
- Промежуточные состояния (журнал записан, указатели нет; `previous` переставлен, `current` нет; оба переставлены, `compose up` и `reload` не выполнены) исправляет повтор той же команды; откат при `previous` = `current` отказывает и показывает последнюю строку журнала.
- Обрыв `ssh` и Ctrl+C: `sshd` при закрытии канала сеанса без tty процесс не убивает (`session_close_by_channel`, `openssh-portable` V_9_6_P1), клиент сигналов на сервер не шлёт; серверный `bash` и `flock` доживают до конца, блокировка держится, пока жив скрипт. Но Go-программы (`docker`, `caddy`) на закрытом stdout получают SIGPIPE даже при `trap '' PIPE`: Ctrl+C во время `compose up` уронил `caddy reload` с кодом 141, и возврат откатил исправную выкладку. Лечится одной строкой – вывод серверной части через `tee -ap deploy.log` (`exec > >(trap '' PIPE; exec tee -ap deploy.log) 2>&1`); с ней Ctrl+C во время `up` доводит выкладку до конца, а на сервере остаётся журнал последней выкладки. Застывший клиент держит блокировку до `timeout 300 tar` – ровно 5 минут.
- `shellcheck` 0.11.0 (образ `koalaman/shellcheck:stable`) чист, кроме намеренных SC2015; образ без `-f gcc` падает на кириллице и молча выдаёт пустой вывод. `shellcheck` 0.11.0 из brew на ноутбуке кириллицу читает и в обычном формате, в том числе при `LC_ALL=C` (проверено оркестратором): `-f gcc` нужен только образу.

Подводные камни:

- macOS bash 3.2: heredoc с апострофом внутри `$(…)` не разбирается, поэтому серверная часть читается `read -r -d '' REMOTE <<'EOF'`, а экранирование для `bash -c '…'` делает `sed`.
- `set -e` не действует внутри функций, вызванных в условии (`if f`, `f && …`): на 3.2 проверено. Прототип делает возврат ловушкой `ERR` с `set -E`, а это хрупко: при `set -E` ловушка наследуется подстановкой команд, и в bash 3.2 сбой команды внутри `$(…)` в проверке запускает возврат прямо в подоболочке. Проверено оркестратором тестом `req() { false; }; [ "$(req)" = 200 ] || …` под `set -Eeuo pipefail` с ловушкой `ERR`: в macOS bash 3.2.57 ловушка срабатывает, в bash 5.2.21 (образ `ubuntu:24.04`, как на `cora`) – нет; `man bash` разницы версий не оговаривает. Прогоны прототипа этот случай не покрывали: `curl` при неверном статусе завершается с кодом 0, а отказа соединения в них не было. Явная проверка каждого шага после переключения вместо ловушки нужна в любом случае: иначе первый «connection refused» во время перезапуска Caddy может запустить возврат исправной выкладки.
- `flock` наследуют дочерние процессы: фоновый потомок держал бы блокировку после выхода скрипта; `docker compose up -d` демонов не порождает.
- `bsdtar` с macOS пишет `LIBARCHIVE.xattr.com.apple.provenance` – нужны `COPYFILE_DISABLE=1` и `--no-xattrs`; на macOS нет `sha256sum`, `shasum -a 256` даёт совместимый формат.
- `APP_VERSION` снимается в подоболочке сборки; `git archive` вместо worktree не годится – номер версии берёт `git` внутри worktree.
- Образ Caddy для `validate` прототип берёт `docker compose config --images | grep '^caddy:'` – хрупко и на Compose 2.40 не проверено.
- Проверка с сервера не видит DNS, `ufw` и внешний 443; выкладка их и не меняет, а Docker публикует порты в обход `ufw`.
- Не проверено: настоящие `docker compose up --wait`, `exec caddy caddy reload`, `docker run … caddy validate` и доступность `127.0.0.1:443` с самого `cora`; наличие `curl` на `cora` (`setup-server.sh` его не ставит); поведение `docker compose exec -T` в сеансе, stdin которого несёт архив.
- Обвязка прототипа (около 100 строк в `~/.cache/lists-deploy-sketch/`): сервис `cora` в compose-проекте `lists` (Ubuntu 24.04, `sshd`, Caddy 2.11), заглушка `docker` с внедрением отказов (`validate`, `up`, `reload`, медленный `up`) и поддельные релизы со сломанными `Caddyfile`. Сценарии запускались вручную, итог читался по выводу, утверждений нет. Это было единственное место, где воспроизводились сбои `reload`, обрыв между перестановками указателей и первая выкладка; по решению автора не сохранена и удалена.

Вариант без каталогов релизов (`rsync --delete` в один `site/`, откат – повторной выкладкой прежнего коммита): около 70–80 строк, но файлы меняются по одному. Workbox 7.4.1 при установке кладёт в предкеш любой ответ ниже 400 без сверки ревизии (`PrecacheStrategy.js`), поэтому новый `sw.js` при старом `index.html` навсегда положит старое содержимое под новую ревизию – до следующей сборки. Откат становится сборкой (8–9 с) и зависит от ноутбука; на ноутбуке `openrsync` (протокол 29), а на `cora` `rsync` не гарантирован. Не рекомендован.

## Приложение. Прототип `deploy/deploy.sh`

Текст прототипа исследования без изменений: worktree `deploy-sketch` удаляется вместе с веткой. Пометки `# >>> opt:X` выделяют необязательные части для подсчёта строк. Отличия итогового скрипта – в разделе «Решение».

```bash
#!/usr/bin/env bash
# Выкладка Watchlist v2 на cora. Прототип исследования, не для слияния.
# Использование: deploy/deploy.sh deploy [коммит] | deploy/deploy.sh rollback
#
# Блоки «# >>> opt:X … # <<< opt:X» – необязательные части, их строки считаются отдельно:
#   a – выборочная проверка сайта с сервера    b – проверка всех файлов по SHA256SUMS
#   c – автоматический возврат при неудаче     d – очистка старых релизов
#   e – предупреждение о незакоммиченном
set -euo pipefail

HOST=${LISTS_HOST:-lists}
ROOT=${LISTS_ROOT:-/opt/lists}
SITE=${LISTS_SITE:-v2.watchlist.acherenkov.com}
# shellcheck disable=SC2206 # LISTS_SSH_OPTS – слова через пробел, для проб
SSH=(ssh -o BatchMode=yes -o ConnectTimeout=15 -o ServerAliveInterval=15 -o ServerAliveCountMax=4 ${LISTS_SSH_OPTS:-})

# Серверная часть: идёт одним сеансом `bash -c` под flock, архив релиза – в stdin.
# Блокировка живёт, пока жив этот bash, а не соединение: обрыв ssh её не отпускает.
read -r -d '' REMOTE <<'EOF' || true
set -Eeuo pipefail
trap '' HUP
root=$1 mode=$2 sha=$3 site=$4 upload=$5
say() { echo "[cora] $*"; }
die() { say "$*" >&2; exit 1; }
cd "$root"
mkdir -p releases tmp
exec 9>>deploy.lock
flock -n 9 || { echo "Другая выкладка или откат уже идут" >&2; exit 75; }
# Вывод идёт через tee в журнал: обрыв ssh не убивает ни скрипт, ни docker и caddy (они на закрытом stdout получают SIGPIPE)
exec > >(trap '' PIPE; exec tee -ap deploy.log) 2>&1
rm -rf tmp; mkdir tmp
cur=$(readlink current || :) prev=$(readlink previous || :)

point() { ln -sfn "$2" "$1.new" && mv -T "$1.new" "$1"; }
up() {
  docker compose -f current/compose.yaml up -d --wait --wait-timeout 120
  docker compose -f current/compose.yaml exec -T caddy caddy reload --config /srv/current/Caddyfile --adapter caddyfile
}
activate() { # хеш включаемого релиза, прежний previous (или пусто)
  printf '%s %s\n' "$(date -u +%FT%TZ)" "$1" >> releases.log
  if [ -n "$2" ]; then point previous "$2"; fi
  point current "releases/$1"
  up
}

# >>> opt:a
verify() { # одна проба сайта с самого сервера; 0 – всё верно
  local f a
  req() { local p=$1; shift; curl -sS --max-time 15 --resolve "$site:443:127.0.0.1" -D tmp/h -o tmp/b -w '%{http_code}' "$@" "https://$site/$p"; }
  for f in index.html sw.js; do
    [ "$(req "$f")" = 200 ] && cmp -s tmp/b "current/site/$f" || { why="$f: статус или содержимое"; return 1; }
    grep -qi '^cache-control: no-cache' tmp/h || { why="$f: нет no-cache"; return 1; }
    ! grep -qiE '^(etag|last-modified):' tmp/h || { why="$f: есть ETag или Last-Modified"; return 1; }
  done
  grep -qi '^x-robots-tag: noindex' tmp/h || { why="нет X-Robots-Tag: noindex"; return 1; }
  [ "$(req sw.js -H 'If-None-Match: *')" = 200 ] || { why="sw.js с If-None-Match: * не 200"; return 1; }
  [ "$(req sw.js -H 'If-Modified-Since: Fri, 01 Jan 2100 00:00:00 GMT')" = 200 ] || { why="sw.js с If-Modified-Since не 200"; return 1; }
  set -- current/site/assets/*; a=${1##*/}
  [ "$(req "assets/$a")" = 200 ] && grep -qi '^cache-control:.*immutable' tmp/h || { why="assets: нет immutable"; return 1; }
  [ "$(req api/x)" = 404 ] || { why="/api/x не 404"; return 1; }
  # >>> opt:b
  local h p
  while read -r h p; do
    [ "$(curl -sf --max-time 15 --resolve "$site:443:127.0.0.1" "https://$site/${p#site/}" | sha256sum | cut -c1-64)" = "$h" ] || { why="$p: сумма не совпала"; return 1; }
  done < current/SHA256SUMS
  # <<< opt:b
}
verify_wait() { # повторяет пробу до срока: Caddy может перезапускаться, а при первой выкладке – выпускать сертификат
  local i; for ((i = 0; i < $1; i++)); do verify && return 0; sleep 2; done; say "проверка сайта не прошла: $why"; return 1
}
# <<< opt:a

# >>> opt:c
restore() { # указатели – ровно как были до выкладки; compose up и reload прежнего релиза
  [ -n "$cur" ] || die "возвращаться некуда (первая выкладка), состояние: $(readlink current || echo пусто)"
  if [ -n "$prev" ]; then point previous "$prev"; else rm -f previous; fi
  point current "$cur"
  up
}
# <<< opt:c

# >>> opt:d
cleanup() { # 5 последних по журналу + current + previous; чужие имена не трогаем
  [ -s releases.log ] || return 0
  local keep d
  keep="$(tac releases.log | awk '!s[$2]++ && n++ < 5 {print $2}') $(readlink current) $(readlink previous)"
  for d in releases/*; do
    [[ $d =~ ^releases/[0-9a-f]{40}$ ]] || continue
    case $keep in *"${d#releases/}"*) ;; *) rm -rf "$d"; say "удалён $d" ;; esac
  done
}
# <<< opt:d

if [ "$mode" = rollback ]; then
  [ -n "$prev" ] && [ "$prev" != "$cur" ] && [ -d "$prev" ] || die "откатываться некуда: previous='$prev', current='$cur', последний в журнале: $(tail -n1 releases.log)"
  target=${prev#releases/} newprev=$cur
else
  target=$sha newprev=$cur
  if [ -d "releases/$sha" ]; then say "релиз уже на сервере"
  elif [ "$upload" = 0 ]; then die "релиз пропал с сервера, повторите команду"
  else
    mkdir tmp/r
    timeout 300 tar -xzf - --no-same-owner -C tmp/r
    (cd tmp/r && sha256sum --quiet -c SHA256SUMS)
    mv tmp/r "releases/$sha"
  fi
  if [ "$cur" = "releases/$sha" ]; then newprev=$prev; fi
fi

img=$(docker compose -f "releases/$target/compose.yaml" config --images | grep -m1 '^caddy:')
docker run --rm -v "$PWD/releases/$target:/release:ro" "$img" caddy validate --config /release/Caddyfile --adapter caddyfile

# >>> opt:c
trap 'trap - ERR; say "неудача после переключения, возвращаю прежний релиз"; restore; die "возврат выполнен"' ERR
# <<< opt:c
if [ "$cur" = "releases/$target" ]; then up; else activate "$target" "$newprev"; fi
# >>> opt:a
verify_wait "$([ -n "$cur" ] && echo 30 || echo 150)"
# <<< opt:a
trap - ERR
# >>> opt:d
cleanup || say "очистка не удалась, повторится при следующей выкладке"
# <<< opt:d
say "готово: $(readlink current)"
EOF

die() { echo "$*" >&2; exit 1; }
tmp=""
cleanup_local() { [ -z "$tmp" ] || { git worktree remove --force "$tmp/wt" 2>/dev/null || :; rm -rf "$tmp"; git worktree prune; }; }
trap cleanup_local EXIT
trap 'exit 130' INT TERM

# Одно соединение: stdin – архив релиза (или /dev/null), аргументы – режим, коммит, нужна ли загрузка.
remote() {
  local q; q=$(printf '%s' "$REMOTE" | sed "s/'/'\\\\''/g")
  "${SSH[@]}" "$HOST" "bash -c '$q' _ '$ROOT' $1 '$2' '$SITE' $3"
}

build() { # коммит -> $tmp/rel.tgz: site/, Caddyfile, compose.yaml, SHA256SUMS
  tmp=$(mktemp -d)
  git worktree add -q --detach "$tmp/wt" "$1"
  (
    cd "$tmp/wt"
    unset APP_VERSION # номер версии должен называть коммит
    pnpm install --frozen-lockfile --prefer-offline
    pnpm --filter watchlist build
  )
  mkdir "$tmp/rel"
  cp -R "$tmp/wt/apps/watchlist/dist" "$tmp/rel/site"
  cp "$tmp/wt/deploy/Caddyfile" "$tmp/wt/deploy/compose.yaml" "$tmp/rel/"
  [ -f "$tmp/rel/site/index.html" ] || die "в сборке нет index.html"
  (cd "$tmp/rel" && find site -type f -print0 | LC_ALL=C sort -z | xargs -0 shasum -a 256 > SHA256SUMS)
  COPYFILE_DISABLE=1 tar --no-xattrs -czf "$tmp/rel.tgz" -C "$tmp/rel" .
}

case ${1:-deploy} in
  deploy)
    sha=$(git rev-parse --verify --end-of-options "${2:-HEAD}^{commit}") || die "нет коммита ${2:-HEAD}"
    # >>> opt:e
    [ -z "$(git status --porcelain --untracked-files=all)" ] || echo "Внимание: незакоммиченное и неотслеживаемое в релиз не попадёт" >&2
    # <<< opt:e
    rc=0; "${SSH[@]}" "$HOST" test -d "$ROOT/releases/$sha" || rc=$?
    case $rc in
      0) remote deploy "$sha" 0 < /dev/null ;;
      1) build "$sha"; remote deploy "$sha" 1 < "$tmp/rel.tgz" ;;
      *) die "ssh завершился с кодом $rc" ;;
    esac ;;
  rollback) remote rollback none 0 < /dev/null ;;
  *) die "использование: $0 deploy [коммит] | rollback" ;;
esac
```
