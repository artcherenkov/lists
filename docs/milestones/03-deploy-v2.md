# Веха 3. Выкладка на v2

Документ вехи: что делаем, какой подход выбран и почему, как проверить. Общие решения – в [плане](../plan.md): раздел «Сервер», «Service worker и обновления», решения 8 и 15, открытый вопрос 2.

## Задача и контекст

Собранный Watchlist выкладывается на `cora` и открывается по `https://v2.watchlist.acherenkov.com`, чтобы проверить PWA на iPhone. Признаки готовности из плана:

- одна команда выкладывает сборку на `cora`, `v2.watchlist.acherenkov.com` её отдаёт;
- порядок отката записан;
- на iPhone приложение ставится на экран «Домой», запускается без сети и обновляется через кнопку обновления.

Учесть из вех 1 и 2 (план, веха 3):

- проверка на iPhone с экрана «Домой»: холодный запуск после смахивания, когда новая версия уже скачана, – сразу новая версия без кнопки обновления; то же после перезагрузки телефона; возвращение из фона – кнопка, версия прежняя; «Обновить» в сети и без сети; запуск без сети; в журнале сервера запрос `sw.js` при запуске и возвращении. Офлайн-проверку делать после первого запуска значка с экрана «Домой» в сети и паузы на скачивание: у приложения с экрана «Домой» своё хранилище, отдельное от Safari;
- `sw.js`, `index.html` и `manifest.webmanifest` отдавать с `Cache-Control: no-cache`, и так, чтобы проверка обновления не получила `304` при новой сборке: ETag по размеру и времени изменения ломается, если у `sw.js` двух сборок совпали размер и время изменения;
- выкладка не должна увозить лишнее: сборка `apps/watchlist` не кешируется Turbo, Vite очищает `dist` сам;
- записать порядок действий при сломанном `sw.js`, код не нужен: исправляющая сборка всегда установится, но включится после перезапуска приложения, а если страница пустая, кнопки обновления не будет. Крайняя мера – сборка `selfDestroying` из `vite-plugin-pwa`;
- сборка без `.git` получает номер версии через `APP_VERSION`;
- если появится политика CSP, встроенный скрипт темы в `<head>` разрешить по хешу.

## Поведение

Решения автора по интервью 2026-10-02 – в скобках номер варианта.

- **Выкладка – одна команда с ноутбука** (например, `pnpm deploy:v2`; `pnpm deploy` – встроенная команда pnpm). Выкладывается любой коммит любой ветки (4A), по умолчанию `HEAD`: номер версии в профиле точно называет выложенное, а на v2 поедут и макеты вехи 5, и ветки вехи 6 до слияния. Сборка – ровно этот коммит при любом состоянии рабочего дерева: незакоммиченные и неотслеживаемые файлы в неё не попадают, и команда об этом предупреждает. Тестов команда не гоняет: они проходят при слиянии (5A).
- Команда собирает `apps/watchlist`, отправляет на `cora` новый релиз, сверяет на сервере суммы файлов и переключает сайт на него. Затем по HTTPS проверяет каждый файл сборки: содержимое совпадает с суммами релиза; всё вне `assets/` – с `Cache-Control: no-cache`, без `ETag` и `Last-Modified`, а запрос `sw.js` с устаревшими `If-None-Match` и `If-Modified-Since` получает `200`; файлы `assets/` – с `immutable`; у страницы – `X-Robots-Tag: noindex`; `/api/` отвечает `404`.
- **Неудача после переключения – автоматический возврат** (5A): если сервер отдал не то содержимое или не те заголовки или упал любой шаг после переключения – `docker compose up` или `caddy reload`, – команда возвращает сайт ровно в состояние до выкладки и завершается с ошибкой. Если сервер не ответил – таймаут, обрыв, нет TLS, – команда повторяет запросы, а после предельного срока сообщает, что проверить не удалось, и релиз не трогает: исправный релиз не откатывается из-за сети ноутбука. При первой выкладке предельный срок дольше – Caddy выпускает сертификат. Если при первой выкладке проверка не прошла, возвращаться некуда: команда сообщает об ошибке.
- **Откат – одна команда**: сайт возвращается на релиз, который был текущим до последнего переключения, с той же проверкой; повторный откат отменяет первый. Откат без прежнего релиза или с удалённым каталогом – отказ с понятным сообщением. Для клиентов откат – обычная новая версия: `sw.js` другой, приложение предлагает обновиться.
- Выкладка коммита, релиз которого уже лежит на сервере, включает этот релиз без сборки; если он уже текущий – только проверка, указатели не меняются.
- Две выкладки или откаты одновременно не идут: вторая команда получает отказ. Агенты работают в разных worktree и могут запустить выкладку одновременно.
- На сервере хранятся последние 5 релизов по порядку включения; текущий и прежний не удаляются никогда.
- **v2 открыта всем** без пароля, с `X-Robots-Tag: noindex`: на ней подставные данные, а данные закроет вход в вехе 6. `/api/*` до появления сервера отвечает `404`.
- Журнал запросов Caddy пишется в журнал Docker с ротацией; по нему видно запросы `sw.js` с iPhone.
- `deploy/README.md` описывает: устройство на `cora` и первичную настройку, выкладку и откат, действия при сломанном `sw.js` (исправляющая сборка установится всегда, но включится после перезапуска приложения; при пустой странице кнопки обновления нет; крайняя мера – сборка `selfDestroying`), обновление образа Caddy и `docker-compose-v2` – они не обновляются сами.
- Проверку на iPhone проходит автор на своём iPhone (7) по чек-листу раздела «Проверка».
- CSP – вместе со входом в вехе 6 (6A): сейчас защищать нечего, а запросы к чужим адресам уже ловит e2e.

## Решение

### Сервер

- **`cora` настраивает агент по `ssh`**, о каждом шаге сообщает автору (1A). Настройка – идемпотентный скрипт в `deploy/`, чтобы повторить её на новом сервере:
  - Docker и Compose – пакеты Ubuntu `docker.io` и `docker-compose-v2`. `docker.io`, `containerd` и `runc` выходят и в `noble-security`, их ставит уже включённый `unattended-upgrades`; `docker-compose-v2` есть только в `noble-updates` и обновляется вручную – это клиент командной строки, а не работающая служба. Обновление `docker.io` перезапускает контейнеры, поэтому у Caddy `restart: unless-stopped`, а запускается он с `Caddyfile` текущего релиза;
  - SSH: свой файл `sshd_config.d/10-lists.conf` с `PasswordAuthentication no` и `PermitRootLogin prohibit-password`. Имя – раньше `50-cloud-init.conf`: `sshd` берёт первое встреченное значение, а файлы читает по алфавиту, поэтому `99-…` проиграл бы `PasswordAuthentication yes` из cloud-init. Перед перезапуском – `sshd -t` и действующие значения через `sshd -T`; после – вход по ключу во втором соединении, пока первое открыто;
  - `ufw`: сначала `allow 22/tcp`, затем 80/tcp, 443/tcp, 443/udp (HTTP/3) и `enable`. Перед включением ставится страховочный таймер (`systemd-run --on-active=5m`), который выключит `ufw` и вернёт прежний `sshd`, если доступ не подтверждён вторым соединением; после подтверждения таймер снимается. Docker публикует порты в обход `ufw`, поэтому правила для 80 и 443 – запись намерения, а настоящая граница – что публикует `compose.yaml`: наружу только Caddy, остальное – на `127.0.0.1` или без публикации. После включения проверить, что контейнер выходит наружу: без этого Caddy не получит сертификат;
  - swap не нужен до базы.
- **Один Compose-проект `lists` на `cora` с одним Caddy и явным `Caddyfile`** (2A): на `cora` живут только Watchlist и Readlist. Caddy принимает 80/443, выпускает сертификат Let's Encrypt для `v2.watchlist.acherenkov.com`, раздаёт статику, а с вехи 6 ведёт `/api/` на сервер. Образ закреплён по версии (на Docker Hub сейчас `caddy:2.11.4-alpine`), обновление – вручную по `deploy/README.md`. Сертификаты – в именованном томе: лимит Let's Encrypt – 5 одинаковых сертификатов в неделю. Админ-API Caddy – по умолчанию, `localhost:2019` внутри контейнера, без публикации: без него `caddy reload` невозможен (`admin off` из прототипа не переносится).
- **Заголовки** – проверенная настройка из «Исследования»: всё вне `assets/` – `no-cache`, без `ETag` и `Last-Modified`, `If-None-Match` и `If-Modified-Since` в запросе срезаются; `assets/` – `public, max-age=31536000, immutable` на ответы 2xx. Запасной путь `@spa` из прототипа не переносится: маршрутов нет.

### Релизы

- **Релиз – каталог на сервере** (3A): `/opt/lists/releases/<хеш коммита>/` с `site/` – сборкой Watchlist, `Caddyfile`, `compose.yaml` и `SHA256SUMS` – суммами файлов `site/`. Всё – из одного коммита, поэтому откат возвращает и сборку, и настройку сервера, и состав сервисов, а позже в релиз войдут Readlist и тег образа сервера. Суммы лежат в релизе, а не на ноутбуке: откат запускают с любой ветки, где нужной сборки нет. `Caddyfile` и суммы лежат вне `site/` и не раздаются.
- Указатели – символьные ссылки `current` и `previous` в `/opt/lists`. Caddy в контейнере видит `/opt/lists` как `/srv` (монтируется каталог, а не ссылка), раздаёт `root /srv/current/site` и запускается `caddy run --config /srv/current/Caddyfile`. Compose запускается из `current/compose.yaml`, пути томов в нём абсолютные: относительный путь через ссылку Docker развернул бы при создании контейнера и закрепил бы релиз.
- Порядок выкладки: доставка во временный каталог → `sha256sum -c` на сервере → переименование в `releases/<хеш>` → `caddy validate` нового `Caddyfile` в контейнере закреплённого образа Caddy (при первой выкладке Caddy ещё не запущен) → переключение `current` и `previous` атомарным `mv -T` → `docker compose up -d --wait` из `current/compose.yaml` (без изменений ничего не делает) → `caddy reload` с конфигурацией текущего релиза (без изменений ничего не делает) → проверка по HTTPS → очистка старых релизов. Ошибка до переключения ничего не меняет; ошибка после – возврат обоих указателей, `compose up` и `reload` прежнего релиза.
- Переходы указателей:
  - выкладка нового или лежащего на сервере релиза R при текущем C: `previous := C`, `current := R`; при R = C – ничего;
  - откат: `current` и `previous` меняются местами; без `previous` или его каталога – отказ;
  - возврат после неудачи: оба указателя – как до операции;
  - первая выкладка: `previous` нет, возвращаться некуда.
- Порядок релизов для очистки – журнал включений `/opt/lists/releases.log`, а не время каталогов: включённый откатом старый релиз не должен попасть под удаление. Строка журнала пишется тем же скриптом на сервере, что переключает указатели, перед переключением: журнал содержит всё, на что когда-либо указывал `current`, последняя строка равна `current`, а ошибка записи случается до переключения и ничего не меняет. Каталог релиза, которого нет в журнале, никогда не включался (например, не прошёл `caddy validate`) и удаляется очисткой. Возврат тоже пишет строку – прежнего релиза, поэтому один релиз встречается в журнале несколько раз, бывает и две строки подряд: место релиза в порядке – его последняя строка, а 5 последних считаются по разным релизам, иначе несколько неудачных выкладок подряд вытеснили бы рабочие релизы. Если журнал не читается или его последняя строка не равна `current`, порядку верить нельзя: очистка ничего не удаляет и падает, иначе пустой или обрезанный журнал стёр бы все релизы, кроме двух (находка ревью среза 4). Неудачные выкладки разных коммитов тоже занимают места в пятёрке: они включались.
- Откат отказывает и тогда, когда `previous` совпадает с `current`: так бывает после обрыва между переключением `previous` и `current`, и обмен местами молча ничего бы не сделал.
- Блокировка – на сервере (`flock` на файле в `/opt/lists`), держится всю операцию. Потеря блокировки (держатель отвалился при сне ноутбука или обрыве сети) прерывает операцию. Ctrl+C даёт текущему шагу на сервере закончиться и останавливает операцию перед следующим: удалённая команда без tty переживает смерть локального `ssh`, и отпущенная раньше блокировка пустила бы вторую выкладку рядом с ней.
- Остановка и возврат (решения оркестратора в срезе 3, выведены из поведения выше): мягкий Ctrl+C начатый возврат не прерывает – бросить его на полпути хуже, чем довести; жёсткий прерывает с предупреждением и командой осмотра. Потеря блокировки возврат не начинает или прекращает: рядом может идти другая выкладка. Остановка во время проверки – не неудача: возврата нет, релиз остаётся включённым. Прежний релиз после возврата по HTTPS не проверяется: возвращаются файлы и `Caddyfile`, уже прошедшие проверку при своей выкладке. Пересмотреть, когда в релиз войдёт сервер с данными.
- **Команда – на TypeScript, запускается Node 24 с ноутбука**, операции на сервере – короткие команды по `ssh`. Решения – чистые функции с unit-тестами в Vitest: переходы указателей, выбор релизов для очистки, оценка результата проверки (годен / вернуть / не удалось проверить). Shell-скрипт не проверить мутацией, которой требует `CODESTYLE.md`. Логика указателей исполняется на ноутбуке из той ветки, с которой запущена команда, поэтому формат состояния на сервере – две ссылки и журнал – менять только вместе с переводом уже лежащего там состояния.
- **Сборка – во временном `git worktree` выкладываемого коммита** на ноутбуке: `git worktree add --detach` во временный каталог, `pnpm install --frozen-lockfile --prefer-offline` из локального хранилища, сборка `apps/watchlist`, удаление worktree. Чистого рабочего дерева мало: номер версии намеренно не учитывает неотслеживаемые файлы (`apps/watchlist/build/app-version.ts`), а новый файл в `public` или класс Tailwind в новом файле `src` попали бы в сборку без пометки «с правками» и закрепились бы в релизе с именем коммита. Если релиз коммита уже лежит на сервере, сборки нет. Номер версии – из git, как сейчас; `APP_VERSION` для сборки без `.git` в этой вехе не нужен. Содержимое сверяется после распаковки сжатия (`Accept-Encoding: identity` или распаковывающий `fetch`), иначе `encode` даст ложное расхождение.

## Основания

- Свой Caddy, а не `ingress` с `caddy-docker-proxy`, как на Viola: на `cora` нет чужих проектов, а один `Caddyfile` читается целиком и проверяется прототипом. С `ingress` статику раздавал бы второй веб-сервер в контейнере, а настройки разошлись бы между метками и его конфигом. Переход на `ingress`, если на `cora` появится чужой проект, недорогой.
- Каталоги релизов, а не образ Docker со статикой, как у текущего Watchlist: выкладка за секунды без пересоздания контейнера, откат – переключение ссылки. Образ вёз бы десятки мегабайт на каждую выкладку.
- Ложный `304` закрыт отказом от валидаторов, а не ETag по содержимому: защита не зависит от шага выкладки, цена – около 20 КБ на проверку обновления.
- `compose.yaml` – часть релиза, а не общий файл: выкладка с любой ветки (4A) иначе откатывала бы порты и сервисы под чужой релиз, а откат не возвращал бы их.
- Принятый риск: после переключения в каталоге релиза нет хешированных файлов прошлой сборки. Страница первого открытия, которой ещё не управляет worker, открытая до выкладки, при ленивой загрузке файла получит `404`; перезагрузка исправляет. - Unit-тесты: переходы указателей – выкладка нового, лежащего и текущего релиза, откат, повторный откат, откат без прежнего, возврат после неудачи, первая выкладка; очистка не трогает текущий и прежний и считает порядок по журналу; оценка проверки – неверное содержимое или заголовок ведут к возврату, сетевой сбой – к «не удалось проверить» без возврата.

## Исследование

### Заголовки статики и ложный `304` (первоисточники и прототип, 2026-10-02)

- Caddy: последний релиз – v2.11.6 (2026-10-01), официальный образ на Docker Hub – 2.11.4, тегов 2.11.5 и 2.11.6 там ещё нет. `file_server` (`modules/caddyhttp/fileserver/staticfiles.go`, `calculateEtag`) считает ETag из времени изменения в наносекундах и размера, содержимое не читает; `Last-Modified` с точностью до секунды ставит `http.ServeContent` из Go. `encode` дописывает к ETag `-gzip`/`-zstd` и снимает суффикс с входящего `If-None-Match`. `etag_file_extensions` есть: ETag из файла-спутника `<имя><суффикс>`, без спутника молча – по времени и размеру.
- Спецификация Service Workers, алгоритм Update: главный скрипт запрашивается с режимом кеша `no-cache`, если `updateViaCache` не `all` (по умолчанию `imports`). По Fetch Standard `no-cache` – условный запрос с `If-None-Match`/`If-Modified-Since` из сохранённого ответа; `304` освежает старый ответ, и побайтовое сравнение решает, что обновления нет. Без валидаторов в сохранённом ответе запрос обычный.
- Прототип на `caddy:2.11-alpine` (2.11.4) и Chromium 153: две сборки с одинаковыми размером и временем изменения `sw.js` дали одинаковый ETag, проверка обновления получила `304`, `updatefound` не наступил. Время изменения совпадает не только случайно: `docker cp` обрезал его до секунд, `tar` по умолчанию хранит секунды, а размер `sw.js` у сборок Vite часто одинаковый – меняются хеши фиксированной длины.
- Workbox 7.4.1 (`PrecacheController`): файлы с ревизией (`index.html`, манифест, иконки) скачиваются при установке с `cache: 'reload'` – мимо HTTP-кеша при любых заголовках; файлы без ревизии (всё в `assets/`) – с `cache: 'default'`, через HTTP-кеш. Сам `sw.js` в предкеш не входит.
- Проверенная настройка: всё вне `assets/` – `Cache-Control: no-cache`, без `ETag` и `Last-Modified` в ответе, а `If-None-Match` и `If-Modified-Since` срезаются в запросе: `ServeContent` сравнивает валидаторы раньше, чем снимаются заголовки ответа, поэтому без срезки клиент со старыми валидаторами всё равно получил бы `304`. Файлы `assets/` – `public, max-age=31536000, immutable` только на ответы 2xx. С ней те же запросы дали `200`, в Chromium обновление нашлось. Цена – `sw.js` (около 17 КБ до сжатия), `index.html` и манифест на каждой проверке скачиваются целиком. ETag по содержимому через спутники тоже работает, но выкладка должна писать спутник на каждый файл, а забытый спутник молча возвращает опасность; полагаться на время изменения – без гарантии, отказ незаметен.
- Каталоги релизов: Caddy в контейнере раздаёт `root /srv/current` через символьную ссылку на каталог релиза; после `ln -s releases/B current.tmp && mv -T current.tmp current` следующий запрос отдаёт новую сборку без перезапуска Caddy. Монтировать нужно каталог, где лежат `releases/` и `current`: смонтированную саму ссылку Docker разворачивает при создании контейнера, и он навсегда остаётся на старом релизе. На файловой системе Linux 180 переключений под 1350 запросами прошли без ошибок; на монтировании с macOS (colima) бывали единичные ошибки – особенность монтирования, на сервере повторить.
- `/api/*` через `handle` с `respond 404` отвечает `404` и не получает `index.html`. Запасной путь на `index.html` для адресов без файла не нужен: маршрутов в приложении нет, а навигацию без сети обслуживает worker. Если понадобится – `rewrite` с матчером `not file`, а не `try_files @имя`: именованный матчер там становится именем файла.

Проверенный фрагмент `Caddyfile` (прототип раздавал `:80` и `root * /srv/current`; в работе – домен, `root * /srv/current/site`, без `admin off` и без запасного пути `@spa`):

```
handle /api/* {
	respond 404
}

handle {
	@revalidate not path /assets/*
	request_header @revalidate -If-None-Match
	request_header @revalidate -If-Modified-Since
	header @revalidate {
		Cache-Control "no-cache"
		-ETag
		-Last-Modified
	}
	header /assets/* {
		Cache-Control "public, max-age=31536000, immutable"
		match status 2xx
	}
	file_server
}
```

`root * …` и `encode zstd gzip` стоят в блоке сайта перед `handle`. `immutable` – только на 2xx, чтобы не закешировать `404` по адресу из `assets/`. Правило `@revalidate` – по пути до любого `rewrite`: если когда-нибудь появится запасной путь на `index.html`, `no-cache` должен остаться и у подменённых адресов – поэтому правило шире трёх файлов из плана.

Не проверено: Safari и WebKit на iPhone – покажет журнал сервера при проверке на телефоне; настоящий HTTPS с доменом; Caddy 2.11.6 в работе.
